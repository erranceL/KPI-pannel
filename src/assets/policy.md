# 研发绩效积分办法 v2.3(试行)

**适用范围**:前端、后端、链端、App 端、架构、DevOps、QA 全体成员及各端 Lead、高级架构师、CTO。

本办法仅适用于研发体系;产品、市场、运营、BD 等非研发岗位如需纳入积分管理,应另行制定对应岗位版本,不直接套用本办法。

---

## 速记卡

> 1. **活按区间定分**:小 1–4 / 中 5–9 / 大 10–24 / 特大 25–50;线上问题处理 3–30;Lead 分活时在区间内取整数定分
> 2. **交付看工期**:工期 ≥ 3 天,实得 = max(0, 1 − 延期天数 × 1.2 / 工期) × 分值;短活只看交付与否;未交付 0 分。要延期,**提前一天说清原因、剩余量、新时间**,同一件事最多重排 2 次
> 3. **线上问题处理**:及时响应基础 3 分;主动发现、下班/周日支援、给对分析推动解决取高位;自己 bug 不计正分,按严重度分级
> 4. **事故与资损**:扣分 = 档位 × 责任 × 报告;新增**资损级 −300**,不封顶、不享高危保护、默认红线、CTO 认定
> 5. **Leader 管理加成**:所带任务实得分的 10% 计入 Lead 正分,每月封顶 15,计入月度/年度与年终奖分子
> 6. **红线别碰 + 有异议就申诉**:私钥、未审批动资产、泄密、隐瞒事故、伪造记录;公示 2 天内找架构师,搞不定升级 CTO

---

## 一、总则

**1.1 目标**

本办法用于量化研发团队工作贡献与风险责任,原则为:按劳取酬、权责对等、安全优先。鼓励承担复杂与高风险任务,不让按流程做事的人为合理风险买单;不奖励躺平与刷分。

**1.2 效力边界**

本办法不替代劳动合同、保密协议、股权/Token 授予协议;冲突时以正式签署文件为准。

**1.3 记录唯一来源**

全部计分依据收敛为两张共享表格:**积分台账**与**问题与事故台账**(模板见附录)。无台账记录的事项不计分、不扣分。

## 二、角色分工

**2.1 Lead**

各端 Lead 负责分配事项时定档、记账(每周约 10 分钟),月底确认本端数据。

**2.2 架构师**

高级架构师负责:跨端事项与定档争议仲裁、特大档复核、各端大档事项月度抽查、月底汇总与公示(约 30 分钟/月)。

**2.3 CTO**

CTO 负责:特大档确认(IM 留言即可)、资损级/P0/P1 事故责任认定、红线调查牵头、年度评级终审。

**2.4 授权**

CTO 可授权高级架构师或对应负责人处理部分事项,但资损级/P0 责任认定、红线处理、年度评级终审仍须 CTO 确认。

## 三、计分规则

**3.1 档位定分**

事项按下表定档,由 Lead 在分配时确定并记入台账,**录入时在区间内取整数**;特大档需架构师或 CTO 确认。

| 档位 | 参考标准 | 分值区间 |
|---|---|---|
| 小 | 半天内:小修复、配置、小接口、小页面 | 1–4 |
| 中 | 1–3 天:常规需求、联调、常规测试 | 5–9 |
| 大 | 3 天–2 周;或虽低于 3 天,但涉及交易、风控、合约、资金、生产环境,且需要 Review / 审批 / 回滚预案的事项 | 10–24 |
| 特大 | 2 周以上,或核心架构/重大安全修复/关键攻坚 | 25–50;超过 1 个月的应拆为多个阶段性特大事项,每阶段单独验收计分 |
| 线上问题处理 | 线上突发问题的响应、定位与推动解决(详见 3.10) | 3–30 |

**3.2 定档留痕与抽查**

大档及以上事项须在台账备注进入该档的理由(工作量/涉及范围/风险面,一句话即可)。架构师每月抽查各端大档事项,发现明显高估或低估的,可在归档前调整。

**3.3 改档规则**

事中发现明显定错档的,Lead 可在交付前修正一次并备注原因。原则上交付后不得改档;但如台账、IM、PR、会议纪要可证明任务范围在执行中发生实质扩大或缩小,可在月度归档前由架构师复核调整一次。已归档后不得改档(伪造、刷分除外)。

**3.4 交付规则(延期公式)**

```
实得 = max(0, 1 − 延期天数 × 1.2 / 原计划工期) × 档位分
```

- 仅对**原计划工期 ≥ 3 工作日**的任务套用上述公式;
- 工期 < 3 天的小活/短中档只用「**全额 / 未交付**」二选一,不套公式;
- **线上问题处理与运维杂项不适用交付系数**(系数恒为 1);
- 未交付或到期才暴露做不完 = 0 分;
- 延期天数指**未预警、超出约定或重排后期限**的工作日数(按期或提前交付即 0 天)。

**3.5 重排期**

提前 1 个工作日以上预警,并说明延期原因、剩余工作量、新完成时间,经 Lead 确认后按新期限判定,不计延期。同一事项原则上最多重排期 2 次,超过 2 次须架构师复核;到期后才暴露无法完成的,按未预警延期处理。

**3.6 需求变更三分类**

| 类型 | 处理 |
|---|---|
| 需求取消、优先级调整、外部依赖阻塞 | 不按延期扣分,按已完成部分计分,Lead 备注原因 |
| 需求范围增加或验收标准实质变化 | 重新定档、重新排期 |
| 文案、样式、字段、配置等轻微调整 | 不自动免责,按原排期或协商小幅调整 |

**3.7 多人协作**

多人事项由 Lead 按人头直接拆分值(如大档 20 分拆主力 12 + 协助 8),台账各记一行,不计算百分比。拆分后总分不得超过该事项档位上限;确需超过的,必须拆为多个独立可验收事项分别记账。

**3.8 专项与协作**

重构、安全修复、降本、自动化、跨端支援一律走大/特大档计分,不另设专项表。修复本人近期引入的问题原则上不计正分;问题未上线且由本人主动发现、主动修复的,不扣分但不加分。是否属于"本人近期引入"以 PR、上线记录、需求归属和台账为准,默认观察期 90 天。同一目标的工作不得拆行重复计分。

**3.9 发布与值班**

常规发布、部署、值班属岗位职责,不逐次计分;由 Lead 按当月强度给"运维杂项"一笔总账:

| 当月强度 | 分值 |
|---|---|
| 常规低强度发布/值班 | 0–3 |
| 多次发布、排障、告警响应 | 4–7 |
| 高频发布、夜间响应、明显影响正常工作节奏 | 8–10 |

**3.10 线上问题处理(3–30)**

线上突发问题的响应与推动解决单独成档,由 Lead/架构师按下述**指引**在区间内定分并备注依据(不硬编系数):

- **及时响应基础分 3**(刻意压低,避免"抢答刷分");
- 区间内**取高位**的情形:主动发现 > 用户发现 > 老板发现;下班后、周日等非工作时间支援;给出正确分析并推动解决(即便最终由他人执行);
- 上限 30,**高于大档、低于特大**;
- **自己 bug 导致的线上问题**:不计本项正分;不一律按事故处理——小问题仅记录、不扣分(4.4),达 P2 及以上才进问题与事故台账扣分。

## 四、扣分规则

**4.1 扣分公式与封顶**

```
实际扣分 = 事故档位分 × 责任系数 × 报告系数
```

单次事故扣分原则上不超过本人近 12 个月正分的 40%;入职未满 6 个月的,按已入职月份正分折算为年化正分后计算封顶。**红线行为、故意违规、隐瞒事故、伪造记录及资损级事故不适用封顶**。扣分封顶不免除权限冻结、复盘、整改、岗位调整等管理措施。

**4.2 事故档位**

| 档位 | 定义 | 扣分 |
|---|---|---|
| 资损级 | 未按流程操作直接导致资产/资金损失 | 300 |
| P0 | 涉及资产、资金、合约、私钥、提现、充值、桥、预言机核心数据;或核心交易、结算、充值、提现等关键服务不可用超过 30 分钟 | 150 |
| P1 | 核心功能不可用、影响大量用户(无资产损失) | 50 |
| P2 | 重要功能异常,影响部分用户或影响测试/发布计划;或因未按明确规范执行,造成跨成员返工超过 0.5 个工作日 | 15 |

**4.3 责任与报告系数**

| 责任 | 系数 |
|---|---|
| 主责(直接导致) | 1.0 |
| 次责(Review/测试/发布环节) | 0.5 |
| 无责(外部攻击、第三方、按流程后不可预见) | 0 |

| 报告情形 | 系数 |
|---|---|
| 主动发现并报告 | 0.5 |
| 被动发现、配合修复 | 1.0 |
| 延迟报告但未扩大影响 | 1.2 |
| 隐瞒、误导、延迟导致影响扩大 | 1.5 + 红线审查 |

**4.4 小问题**

样式、文案、内部文档类小问题原则上不扣分,仅记入问题与事故台账。30 天内同类问题由同一责任人重复 2 次,且公司已有明确规范或检查清单的,按 P2 处理;尚无规范或清单的,优先补充流程,不直接升级扣分。

**4.5 单一处罚**

同一事故只扣一次分,不叠加"绩效归零""取消评优"等处罚。资损级/P0/P1 由 CTO 认定,P2 可由架构师认定。**例外**:资损级事故为本条例外,其触发的"相关期间正分失效(6.2)"可与本档基础扣分叠加。

## 五、高风险保护

**5.1 保护条件与效果**

合约、桥、资金、私钥、生产环境类操作,凡走完 **Review + 上线审批 + 回滚预案**并留痕(PR 记录 + IM 审批留言即可)的,出问题最多按次责处理,主动报告再减半。但当事人明知风险未披露、测试记录明显缺失、Review 信息不完整或审批材料与实际操作不一致的,不适用本保护;绕过流程的不适用本保护。**资损级事故(未按流程导致资产损失)不适用本高危保护。**

**5.2 双人复核**

上述高危操作必须双人复核,禁止单人闭环。

## 六、安全红线

**6.1 红线清单**

触碰以下任一条,立即冻结权限,由 CTO 牵头专项调查(当事人可申辩),处理措施从取消激励至解除合作、依协议追责,由管理层决定:

1. 私自导出、复制、传播私钥、助记词、生产密钥;
2. 未经审批操作链上资产、合约升级、提现或资金账户;
3. 故意或重大过失泄露源码、架构、资金逻辑、用户数据、商业机密;
4. 故意隐瞒资产风险或事故;
5. 伪造记录、删除证据、误导调查。

未构成故意或重大过失的信息误发、误传等情形,由专项调查根据影响范围、是否及时报告、是否造成损失,按问题与事故通道处理。

**6.2 红线积分处理**

红线不按普通事故扣分公式处理,但可影响相关期间正向积分与年度激励:红线成立的,当事人自行为发生月至发现月期间与该行为相关的正向积分失效;存在故意隐瞒、持续违规或伪造记录的,可由管理层决定扩大至处理完成月。**资损级事故同时构成红线的,其基础扣分(4.2)与本条正分失效可叠加**;正分失效为管理层手动执行的措施,系统不自动计算。

## 七、Leader 连带与管理加成

**7.1 连带情形**

因 Lead 管理失误(未安排 Review、排期明显不合理)导致的事故,Lead 连带成员实际扣分的 30%;Lead 批准违规操作的,连带 100% 并触发红线审查。

**7.2 不连带情形**

成员私自绕过流程、隐瞒导致的问题,Lead 不连带。

**7.3 管理加成**

每位 Lead 就其管理的事项获得正向**管理加成**:

```
管理加成 = 所带任务"实得分"合计 × 10%(按月汇总),单 Lead 每月封顶 15 分
```

- 不含 Lead 本人任务;季/年视图按月分别封顶后再相加;
- 计入**月度总分、年度有效积分与年终奖分子**,口径一致;
- 所带任务出问题的连带扣分仍按 7.1 计 30%;
- 无 Lead 的端(DevOps/QA/架构)其加成归口架构师或 CTO,受同一封顶约束。

## 八、月度流程与公示

**8.1 月度流程**

Lead 平时记台账 → 月底架构师加总、公示 2 个工作日 → 异议由架构师仲裁,仲裁不服升级 CTO → 归档。已归档积分不追溯(伪造、刷分除外)。

**8.2 公示范围**

试运行期间**成员侧仅公示总分区间**(不做匿名排名);实名明细仅本人、所属 Lead、架构师、CTO 可见,本人可随时查阅自己的全部明细。是否转为实名公示,由试运行结束后管理层根据团队反馈决定。

**8.3 刷分处理**

拆行重复计分、挂名、包装自己造成的问题等行为,查实后该部分积分作废,累犯影响年度评级。

## 九、年度评级与分配

**9.1 年度评级**

年底由 CTO + 架构师 + 各端 Lead 召开一次评级会(约 1 小时),按年度有效积分排序结合台账评定等级。积分排名是必要条件而非充分条件。

年度有效积分 = max(全年正分(含管理加成) − 全年扣分, 0)。

| 等级 | 条件 | 年度绩效系数 |
|---|---|---|
| S | 原则上不超过团队 15%;有特大档关键贡献;无 资损级/P0/P1 主责 | 1.5 |
| A | 原则上不超过团队 40%;年度积分明显高于团队中位数;无 资损级/P0 主责 | 1.2 |
| B | 达到岗位要求,交付稳定(默认档) | 1.0 |
| C | 低于岗位要求,或年度有效积分低于团队中位数 50% | 0.5 |
| D | 年度有效积分为 0,或红线成立,或持续无法胜任 | 0 |

资损级/P0 主责封顶 B 级;红线调查期间暂缓评定。团队人数较少导致比例无法整除时,由评级会按上述条件实质判断。

**9.2 年终奖**

```
实际年终奖总池 = 公司年度奖金预算 × 经营系数
个人年终奖 = 实际年终奖总池 × ( 个人年度有效积分 ÷ 全员年度正向积分总和 )
```

经营系数(0–1.2)由管理层于年度总评前公布,仅用于确定实际总池,不重复计入个人公式。

分母采用全员正向积分总和:任何人的扣分只减少本人份额,不流为他人收益;因扣分导致未分配的部分归公司留存,不自动二次分配。单人份额超过全员平均 3 倍的,管理层复核数据真实性。如全员年度正向积分总和为 0,则不按本公式分配,由管理层另行决定是否发放及发放方式。

**9.3 积分与激励衔接**

本版**不再设 Token 配额计算公式**。积分是未来 Token / 股权激励分配的**重要参考输入之一**,具体分配方案由管理层在具备条件时另行制定。管理层亦可在**季度**维度参照 9.2 同一"反零和"口径进行阶段性激励(季度池 = 季度预算 × 经营系数,按季度有效积分占比分配),口径与年度一致。

## 十、附则

**10.1 试运行**

本办法试运行 1 个季度:仅记台账与公示,不挂钩奖金;第 2 季度起关联月度绩效;自年度周期起接入年终奖。

试运行期间由架构师按月跟踪五项指标,作为转正式版的修订输入:

1. 大档占比是否异常偏高;
2. 重排期次数是否过多;
3. 小问题是否重复记录但无流程改进;
4. 各端 Lead 定档尺度是否明显不一致;
5. 线上问题处理条数/人是否异常偏高(防"抢答刷分")。

**10.2 新员工**

入职未满 3 个月:扣分减半,不参与排名,不担任高危操作主责(管理层特批除外)。红线行为、故意隐瞒、伪造记录、未审批操作资产及资损级事故不适用扣分减半。

**10.3 申诉**

公示期内提出:定档争议由架构师裁定;事故责任由 CTO 裁定;奖金、纪律争议由管理层集体复核,CTO 不单独终裁。

**10.4 修订与解释**

修订由 CTO 发起,公示 3 个工作日后生效;变更不追溯已归档积分;解释权归公司管理层。
